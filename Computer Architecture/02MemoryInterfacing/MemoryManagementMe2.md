# Memory Management

## Section 1: The Memory Hierarchy & Addressing Mechanics

### 1.1 The Memory Hierarchy
Memory is architected hierarchically to resolve the physical engineering trade-offs between processing speed, capacity limitations, and manufacturing costs.

```bash
[ Registers ]
        │
        V
[ Cache Memory  ────► (L1, L2, L3)]
        │
        V
[ Main Memory   ────► (RAM / Primary Physical Memory)]
        │
        V
[ Secondary Storage ────► (SSD / HDD / Logical / Virtual / Auxiliary Disk)]
───────────────────────────────────────────────────────────────────────────►
► Capacity Increases
► Access Time / Latency Increases
► Per-Unit Cost Decreases
```

#### Core Architectural Constraints
* **CPU Fetch Constraint:** The CPU executes instructions and manipulates data directly out of Registers, Caches, or Main Memory (RAM). It cannot directly fetch data from secondary storage blocks. Doing so would cause massive storage-latency stalls, freezing the CPU pipeline.
* **Modern Multi-Level Cache Topologies:** 
  * **L1 Cache:** Roughly 32 KB to 64 KB per core. It runs at the CPU clock speed with near-zero latency.
  * **L2 Cache:** Roughly 512 KB to 1 MB per core. Fast, low-latency intermediate storage.
  * **L3 Cache:** Roughly 16 MB to 64 MB. Shared across all execution cores on the processor die.

---

### 1.2 Locality of Reference (LoR)
Locality of Reference is the behavioral phenomenon where software applications access a localized fraction of their storage space at any given time. This pattern allows a small, fast memory layer (Cache) to satisfy the vast majority of CPU requests, keeping both Cache and RAM hit ratios consistently above 90%.

1. **Spatial Locality:** If a specific memory location is referenced, nearby memory locations are highly likely to be accessed soon.
   * *Backend Engineering Context:* Processing item sequences in flat continuous arrays, executing program code sequentially, or reading database records loaded contiguously into memory buffers.
2. **Temporal Locality:** If a memory location is referenced, the exact same location is highly likely to be accessed again in the near future.
   * *Backend Engineering Context:* Loop executions (`for` / `while`), localized index variables, recycling configuration objects, or caching high-frequency session records (often managed using Least Recently Used policies).

---

### 1.3 System Workflows & Performance Metrics

#### Memory Mapping Workflows
Data moves sequentially through the memory levels in structured, fixed-size chunks. The OS and CPU hardware collaborate via address translations:
* **Operating System (OS Perspective):** Translates the large **Logical Address (LA)** generated by the CPU according to the secondary virtual memory boundary into a **Physical Address (PA)** pointing to RAM via Page Tables.
* **Computer Architecture (COA Perspective):** Maps the **Physical Address (PA)** into a specific **Cache Address/Index** to determine if the target data block currently resides inside the cache lines.

#### Performance Metrics
* **Cache Hit:** The requested data element is successfully found inside the cache tier.
* **Hit Ratio (\(H\)):** The fraction of total memory accesses satisfied by the cache tier.
\[\text{Hit Ratio } (H) = \frac{\text{Cache Hits}}{\text{Total Access Requests}}\]
* **Hit Latency (\(T_c\)):** The direct execution time required to search and fetch the data out of the cache.
* **Cache Miss:** The requested data element is missing from the cache, forcing a lookup down the slower layers of the hierarchy.
* **Miss Latency / Penalty (\(T_m\)):** The total time required to look up, fetch, and swap the missing block from Main Memory (or disk) into the cache layer.

---

### 1.4 Memory Unit Divisions
To enforce smooth, uniform block-level data transfers without structural fragmentation, different layers of storage are partitioned into equal-sized units:
* **Secondary Memory:** Divided into fixed-size blocks called **Pages** (Typically 4 KB in modern OS environments).
* **Main Memory (RAM):** Divided into matching partitions called **Blocks** (COA engineering term) or **Frames** (OS engineering term).
* **Cache Memory:** Divided into smaller fixed-sized structural units called **Cache Lines** or **Cache Blocks** (Typically 64 Bytes).

---

### 1.5 Binary Scaling & Mathematical Addressing Framework

#### Engineering Scaling Reference
* \(1 \text{ Kilo (K)} = 10^3 \approx 2^{10} = 1,024\)
* \(1 \text{ Mega (M)} = 10^6 \approx 2^{20} = 1,048,576\)
* \(1 \text{ Giga (G)} = 10^9 \approx 2^{30} = 1,073,741,824\)
* \(1 \text{ Tera (T)} = 10^{12} \approx 2^{40}\)
* \(1 \text{ Peta (P)} = 10^{15} \approx 2^{50}\)

#### Core Structural Formula
\[\text{Memory Size (MS)} = (\text{Number of Unique Addressable Locations}) \times (\text{Size of Each Location})\]
*By engineering convention, modern systems are **Byte-Addressable** by default, meaning each addressable location stores 1 Byte (8 bits) of data.*

* **Deriving Memory Size from Address Bits (\(n\)):**
  If the system address field spans \(n\) bits, the total number of unique addressable locations equals \(2^n\).
  \[\text{Example for } n = 17 \text{ bits}: 2^{17} \times 1 \text{ Byte} = 2^7 \times 2^{10} \times 1 \text{ B} = 128 \text{ KB}\]
* **Deriving Address Bits (\(n\)) from Memory Size:**
  \[n = \lceil \log_2(\text{Number of Unique Addressable Locations}) \rceil\]
  \[\text{Example for a 32 GB Byte-Addressable Memory Size: } \frac{32 \text{ GB}}{1 \text{ Byte}} = 32 \times 2^{30} = 2^5 \times 2^{30} = 2^{35} \text{ locations.}\]
  \[\text{Required Address Field Length} = \log_2(2^{35}) = 35 \text{ bits}\]

## Section 2: Cache Mapping & Replacement Policies

### 2.1 Principles of Memory Mapping
Data is moved across hardware boundaries inside multi-word structures called **Blocks** to protect spatial locality. Cache mapping algorithms determine exactly how these large physical memory blocks hash or map down into the smaller available slots (lines) of a cache.

---

### 2.2 Cache Mapping Algorithmic Strategies

#### A. Direct Mapping (One-to-Many Hash Mapping)
Each block of Main Memory maps to exactly **one predetermined line** within the cache module.
\[\text{Cache Line Number (Index)} = (\text{Main Memory Block Number}) \pmod{\text{Total Cache Lines}}\]

* **Trade-off:** Minimal lookup complexity (\(O(1)\) evaluation time) and cheap hardware components. However, it suffers heavily from **Conflict Misses (Thrashing)** if an application sequentially calls different memory blocks that map onto the same index line.
* **Mathematical Blueprint Example:**
  * Total System Memory: \(64 \text{ Words} \implies 2^6 = 6 \text{ bit Physical Address field}\).
  * Block Capacity: \(4 \text{ Words per Block} \implies 2^2 = 2 \text{ bits Block Offset}\).
  * Total Main Memory Blocks: \(\frac{64}{4} = 16 \text{ Blocks} \implies 2^4 = 4 \text{ bits for Block Numbering}\).
  * Cache Lines: \(4 \text{ Lines} \implies 2^2 = 2 \text{ bits Cache Line Index}\).
  * **Resulting Address Bit Breakdown:**
    * **Block Offset:** \(\log_2(4) = \mathbf{2 \text{ bits}}\) (Locates the word position within a block).
    * **Cache Line Index:** \(\log_2(4) = \mathbf{2 \text{ bits}}\) (Identifies the target cache slot).
    * **Tag Bits:** \(\text{Total Bits} - \text{Line Index} - \text{Block Offset} = 6 - 2 - 2 = \mathbf{2 \text{ bits}}\) (Stored in the cache directory to verify block identity).

---

#### B. Fully Associative Mapping (Many-to-Many Mapping)
A block of Main Memory can be dynamically housed within **any freely available line** anywhere inside the cache module.
* **Trade-off:** Eliminates structural conflict misses entirely. However, searching for a data word requires inspecting the entire cache tag directory. To make this lookup fast, hardware designs require dedicated, expensive parallel circuits called **Hardware Comparators**.
* **Tag Directory Bit Formula:**
  \[\text{Tag Bits} = \text{Total Address Bits} - \text{Block Offset Bits}\]
  \[\text{Total Tag Directory Space Required} = (\text{Total Number of Cache Lines}) \times (\text{Tag Field Bit Count})\]

---

#### C. Set-Associative Mapping (Hybrid / \(K\)-Way Strategy)
The internal layout of the cache lines is segmented into equal sub-groups called **Sets**. Each individual set holds exactly \(K\) lines (known architectural layouts include 2-Way, 4-Way, 8-Way, or 16-Way Set-Associative Caches).
\[\text{Target Cache Set Index} = (\text{Main Memory Block Number}) \pmod{\text{Total Structural Sets}}\]

* **Trade-off:** Provides a high-performance middle-ground. A block routes directly to an explicitly calculated set (like Direct Mapping), but once inside that target set, it can safely occupy any of the \(K\) empty lines (like Fully Associative), lowering conflict occurrences.
* **Set Bit Calculation:**
  \[\text{Set Index Bits} = \log_2(\text{Total Number of Sets})\]
  \[\text{Where: Total Sets} = \frac{\text{Total System Cache Lines}}{K}\]

---

### 2.3 Cache Eviction & Replacement Policies
When a cache miss occurs and the calculated cache set or location slot is entirely filled with active data, an existing block must be evicted to make room for the newly requested data block.

1. **FIFO (First-In, First-Out):**
   * **Logic:** Tracks chronological entry steps. Evicts the specific block that has resided in the cache space for the longest continuous timeframe.
   * **Flaw (Belady’s Anomaly):** For non-localized linear lookup patterns, increasing the total capacity of the cache lines can paradoxically trigger an increase in cache misses, degrading pipeline throughput.
2. **Optimal Replacement Policy (MIN / Belady’s Theoretical Rule):**
   * **Logic:** Analyzes the future code execution path and evicts the data block that will not be accessed by the processor for the longest time.
   * **Real-World Status:** Strictly impossible to put into actual hardware circuits because a CPU cannot see down an unpredictable runtime path. It is used strictly as a benchmark baseline to evaluate the efficiency of other policies.
3. **LRU (Least Recently Used):**
   * **Logic:** Uses application history as a proxy for the future. Evicts the specific block that has gone unaccessed for the longest duration.
   * **Overhead Constraint:** Requires hardware to manage age counters, status flags, or state tables during every memory read/write operation to track exact usage order, adding silicon and execution overhead.

## Section 3: Performance Modeling, Access Types, & Coherence

### 3.1 Structural Classification of Cache Misses (The 3 C's)
* **Compulsory Miss (Cold Miss):** Occurs when the processor requests a particular data block for the very first time. Because the application has just initialized or has not requested this block before, the cache is clear of it, making a miss unavoidable.
* **Capacity Miss:** Occurs when the cache cannot hold all the operational blocks required by the program during loop executions because the program's working set size is larger than the total cache capacity. This can happen across **all** cache configurations if the active application data footprint overflows the total storage bytes of the cache.
* **Conflict Miss (Collision / Interference Miss):** Occurs when multiple main memory blocks map onto the exact same set index or direct cache line, causing repeated mutual evictions even though large portions of the surrounding cache space are completely empty. This issue is found **only** in Direct-Mapped and Set-Associative designs; Fully Associative caches are immune.

---

### 3.2 Advanced Memory Access Time (AMAT) Architectures
Hardware layouts route data requests down cache levels using two distinct connection paths:

#### A. Sequential / Hierarchical Access Architecture
Memory tiers are linked in a chain. The processor looks up the fastest level (L1) first. It only continues to slower levels if a miss occurs.


##### AMAT Mathematical Formula
Let \(H_n\) match the local hit rate of level \(n\), and \(T_n\) equal the precise access latency of level \(n\).
\[\text{AMAT} = (H_1 \cdot T_1) + (1 - H_1)H_2 \cdot (T_1 + T_2) + (1 - H_1)(1 - H_2)H_3 \cdot (T_1 + T_2 + T_3)\]
*Architectural Impact:* Because the system must wait to check and miss a level before starting a search on the next layer, access latencies pile up sequentially (\(T_1 + T_2\)).

#### B. Parallel / Simultaneous Access Architecture
Every memory level is tied directly to the core CPU address bus layout. The processor kicks off a look-up across all tiers at the exact same moment.


##### AMAT Mathematical Formula
\[\text{AMAT} = (H_1 \cdot T_1) + (1 - H_1)H_2 \cdot (T_2) + (1 - H_1)(1 - H_2)H_3 \cdot (T_3)\]
*Architectural Impact:* Because all searches start at the same time, if L1 misses but L2 hits, the data block arrives in exactly \(T_2\) time, without adding \(T_1\).
*Boundary Condition:* For analytical calculation models, the data is assumed to reside in the final fallback tier, establishing \(H_{\text{last}} = 1\).

### 3.3 Cache Write Policies & Coherence

Because caches store temporary local copies of data, updating values in one layer while leaving old data in another creates a **Data Inconsistency** problem. This is especially challenging in multi-core backend environments when multiple independent cores cache a single shared state variable.

#### Layer Coherence Mitigation Policies

##### 1. Write-Through
* **Logic:** Every write command writes data to both the local cache line and Main Memory concurrently.
* **Advantage:** Provides the highest data consistency. Main memory is never out of sync.
* **Disadvantage:** High write latency penalty; the CPU pipeline must stall and wait for the slower Main Memory write cycles to complete.
* **Hardware Footprint:** Simple; no extra state-tracking bits (like a Dirty Bit) are required.

##### 2. Write-Back
* **Logic:** The CPU writes data updates *only* to the local cache line. The cache line sets a tracking flag called a **Dirty Bit**. The updated block is written back to Main Memory *only* when that cache line is evicted by a replacement algorithm.
* **Advantage:** High throughput and minimal latency. Writes execute at fast cache memory speeds.
* **Disadvantage:** Temporary data inconsistency; Main memory holds stale data until the modified cache line is evicted.
* **Hardware Footprint:** Requires a dedicated **Dirty Bit** per cache block (\(0 = \text{clean/unmodified}\), \(1 = \text{dirty/modified}\)).

#### Core-to-Core Coherence Protocols (Snooping)
While layer write policies manage consistency between one cache and main memory, multi-core systems require specialized hardware rules to maintain data integrity across distinct core caches:
* **Bus Snooping:** Every core continuously monitors (snoops) the shared data bus. If Core A writes a new value to its local cache using a Write-Through mechanism, Core B catches this on the bus and marks its own local copy of that variable as **Invalid**.
* **MESI Protocol Standard:** A standard hardware state machine protocol that tracks the lifecycle of every cache line across 4 distinct states:
  * **M**odified: The local line has been updated (dirty) and exists only in the current cache.
  * **E**xclusive: The local line matches Main Memory and is present *only* in the current cache.
  * **S**hared: The local line matches Main Memory and is mirrored in other core caches.
  * **I**nvalid: The local line contains stale data and cannot be read.

## Advance topics:
1. Split Cache vs. Unified Cache (Structural Design)
  - What it is: Caches can be designed to store either specific types of data or everything together.
    - Split Cache: The cache is physically divided into an I-Cache (Instruction Cache) and a D-Cache (Data Cache).
    - Unified Cache: A single cache structure stores both instructions and execution data dynamically.
  - Why it matters: Modern processors use a Split Cache at the L1 level to allow the CPU to fetch instructions and read/write data at the exact same time without stalling the pipeline (structural hazards). L2 and L3 caches are typically Unified to maximize space efficiency.
  
2. Cache Write Allocation Policies (Miss Behaviors)
Your notes accurately explain what happens on a cache write hit (Write-Through vs. Write-Back), but they missed how the hardware behaves on a cache write miss (when the CPU tries to write to a memory address that isn't in the cache).
  - Write Allocate (Fetch-on-Write): The block containing the target address is loaded from Main Memory into the cache first, and then the write update is performed. (Almost always paired with Write-Back caches).
  - No-Write Allocate (Write-Around): The data is written directly to the slower Main Memory without loading the block into the cache. (Almost always paired with Write-Through caches to avoid unnecessary memory transfers).
  
3. Multi-level Cache Inclusive vs. Exclusive Policies
When you chain L1, L2, and L3 caches together, hardware designers use explicit rules regarding data replication:
  - Inclusive Cache: An item found in the L1 cache must also exist in the L2 and L3 caches. If an item is evicted from L3, it is automatically knocked out of L1.
  - Exclusive Cache: An item can only exist in exactly one cache level at a time. If data is loaded into L1, it is entirely deleted from L2, maximizing the total unique storage area across the chip.
  - Non-Inclusive Cache: Data can exist haphazardly across levels without strict binding rules (standard in many modern Intel/AMD layout topologies).
  
4. Advanced LRU Implementation Approximations
Your notes correctly mention that tracking pure LRU requires high overhead (tracking age matrices or hardware counters on every CPU cycle). In production systems, hardware uses cheaper approximations:
  - Pseudo-LRU (PLRU): Uses a binary tree structure of single status bits to track paths of recent access. It only requires \(N-1\) bits for an \(N\)-way set associative cache, making it extremely cheap to build in silicon while achieving a \(>95\%\) match to true LRU performance.
